# Bound NexaUI Settings in the development desktop

5 November 2026. The existing development owner now supports an explicitly
selected NexaUI Settings view through dock/search and the actual DRM carrier.
The default stays SDL. The original model, app slots and process/pipe ownership
remain separate from presentation; this is not normal authority admission or
the accepted final Settings UI.

## Implementation

`start --desktop --settings-ui nexaui` selects the reviewed Release/Debug paths
in [the input pin](../../../spec/nexaui-inputs.json). The controller checks
candidate/version/profile, original model hashes, ownership/modes, exact app/
library bytes and bounded raw build metadata. It records a canonical binding
before start effects and passes its digest to the original ordinary-user
supervisor, which repeats the check before creating children.

Each fresh Settings spawn rechecks that selection. Drift returns the existing
error reply without a new process, default-toolkit fallback or stopping the
desktop. An existing live child is reused through its original handle. A fresh
request after exact input restoration can create a new process after the old
one and its pipe have retired. New version1 record fields retain the selection;
old records keep their SDL meaning. Closed retries do not reread/adopt a newer
candidate. The six other desktop runtime images plus selected app/library are
recorded; the unused SDL Settings image is omitted for this profile.

These same-account mutable-file checks are developer consistency, not publisher
trust, a sealed store, atomic exec/image admission or a security boundary against
the build account. No normal authority capability or policy is opened. No new
registry, bus, permanent helper or package is installed. See
[running it](../../../spec/development-session.md) and the
[consumer boundary](../../../spec/nexaui.md).
